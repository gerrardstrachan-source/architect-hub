# H2 — Prospective Future-Learning / Structural-Transfer Experiment

## Version / status

**Specification:** v0.2  
**Status:** DESIGN-LOCK CANDIDATE — NOT EXECUTABLE  
**H1:** frozen and closed; no H1 modification is permitted for H2.

H2 is a prospective experiment intended to challenge the explanatory adequacy of the surviving ACT-R account with respect to **future learning consequences**. It does not assume an understanding mechanism and does not define a residual in advance.

The design is deliberately split into three layers:

1. **World definition** — what objectively occurs.
2. **Learner interface** — what information is available to the model.
3. **Model realization** — how an ACT-R learner may internally represent and learn from that information.

The third layer must never be confused with a property of the world.

---

## 1. Formal scientific question

> After exposure to the same observable task elements and matched immediate performance, does prior learning about an objectively defined structural regularity produce a reproducible pattern of future-learning consequences that the fully stipulated ACT-R account cannot adequately explain?

The target is not a one-shot transfer advantage. The target is a **pre-specified multi-condition trajectory signature** across structurally controlled future tasks.

A residual is admissible only after the surviving ACT-R account has been given its legitimate mechanisms and the observed trajectory remains outside its tested explanatory range.

---

## 2. Formal world

### 2.1 Trial object

Every trial presents an observable tuple:

`(c, x, y) → action`

where:

- `c` = context token;
- `x` = binary observable feature, `0` or `1`;
- `y` = binary observable feature, `0` or `1`;
- `action` ∈ `{A0, A1}`.

No trial presents a field called `rule`, `relation`, `structure`, `xor`, or equivalent.

### 2.2 Base relational regularity

For the core structured family, the objectively defined action rule is:

`A0 if x XOR y = 1; A1 otherwise.`

Equivalently:

| x | y | relation r=x XOR y | correct action |
|---|---|---:|---|
| 0 | 0 | 0 | A1 |
| 0 | 1 | 1 | A0 |
| 1 | 0 | 1 | A0 |
| 1 | 1 | 0 | A1 |

The learner receives only the observable features and outcome feedback. The name of the relation is never supplied.

This definition is a **world property**, not an assumed learner representation.

### 2.3 Matched surface family

Future-task variants are generated by a deterministic encoding of the same underlying binary relation. Encoding changes must preserve the formal relation while changing only the declared surface variables.

Permitted surface encodings include:

- feature renaming (`x↔y`);
- symbol renaming for feature values (`0↔1` within one feature, with the corresponding truth table transformation fixed before data collection);
- context-token renaming;
- order reversal of displayed features.

No encoding may change the number of informative features, the response set, the feedback rule, or the underlying relation unless that condition is explicitly designated as structural conflict.

---

## 3. Learner interface

For every trial the model has access only to:

1. the current context token `c`;
2. the current observable values `x` and `y` (or their pre-registered surface encoding);
3. the available action set `{A0,A1}`;
4. the feedback consequence after action selection during training blocks;
5. normal internal ACT-R state arising from prior experience.

The model is **not** given:

- the name of the relation;
- a symbolic rule statement;
- a precomputed `x XOR y` feature;
- a structure label;
- future-task identities;
- the correct action before action selection.

Ground truth remains external to the learner and is supplied only through the stipulated environmental consequence.

This prevents the experiment from granting ACT-R the target abstraction by construction.

---

## 4. Training histories

H2 compares two training-history classes that use the same observable feature vocabulary, response vocabulary, trial counts, exposure opportunities, and feedback schedule.

### 4.1 Structured history H-S

Training instances are drawn from the base relational family with repeated exposure to informative combinations sufficient to identify the regularity from the observable cases.

The exact trial order will be frozen before execution. The final training fixture must satisfy:

- identical numbers of trials across H-S and the matched control history H-C;
- identical marginal counts of `c`, `x`, and `y`;
- identical action-set availability;
- identical feedback schedule;
- identical maximum feature/display complexity;
- no direct presentation of the relation label.

### 4.2 Matched control history H-C

H-C uses the same observable marginal distribution and exposure counts, but the action contingencies are constructed so that the same immediate performance can be obtained without a single stable cross-case relation of the H-S kind.

The control is not described as “random” in the executable specification. Its exact contingency table and frozen order must be generated and hashed before execution.

### 4.3 Immediate-performance matching

The target is not merely equal terminal accuracy.

Before future-task exposure, histories are admissible for comparison only if they satisfy the pre-specified matching window for:

- aggregate accuracy;
- trial-by-trial accuracy distribution;
- trials-to-criterion, where criterion is defined;
- response-time distribution, where the chosen ACT-R realization produces a valid observable latency;
- action repertoire;
- exposure count.

**State matching is not assumed.** Any internal ACT-R differences produced by the histories are treated as the potential explanatory variable and must be measured through model-state diagnostics where the architecture exposes them.

If a matching criterion cannot be met without post hoc selection, the corresponding history pair is rejected rather than repaired after observation.

## 5. Future-task conditions

All future conditions use fixed, precomputed trial fixtures. Each condition has an explicit invariant and manipulated variable.

### A — Compatible extension

**Invariant:** same underlying relation and same observable feature structure.  
**Manipulated variable:** novel instances within the previously experienced structural family.

Purpose: test ordinary extension where prior relational regularity, if learned, remains directly useful.

### B — Structural recombination

**Invariant:** same primitive feature vocabulary.  
**Manipulated variable:** previously experienced feature values occur in novel combinations not jointly experienced during training.

Purpose: test whether learning survives recombination rather than requiring memorized conjunctions.

### C — Surface transformation

**Invariant:** same underlying relational mapping.  
**Manipulated variable:** surface encoding is transformed by a frozen bijection that preserves the formal relation.

Purpose: separate relational transfer from direct surface matching.

### D — Structural conflict

**Invariant:** same primitive surface vocabulary and response set.  
**Manipulated variable:** the previously useful relation is replaced by a formally different mapping in the future block.

Purpose: test interference, relearning, and adaptation when prior regularity becomes misleading.

### 5.1 Condition-equivalence controls

For every pair of future conditions being compared, the following must be either identical or explicitly modeled:

- number of trials;
- number of unique states;
- feature cardinalities;
- response cardinalities;
- stimulus presentation complexity;
- feedback availability;
- deadline structure;
- block length;
- exposure count;
- criterion definition;
- retention interval, if any.

Any manipulated variable not listed in the condition definition is a design violation.

---

## 6. Primary outcome measures

Primary measures are ordered to avoid allowing one favorable statistic to define success retrospectively.

1. trial-by-trial accuracy;
2. trials-to-criterion;
3. error-transition sequence;
4. action-selection trajectory;
5. transfer accuracy on first exposure to each future condition;
6. interference/relearning cost in D;
7. retention across a pre-specified separation interval, if included;
8. response latency distribution where validly observable.

Secondary measures may include production-selection traces, utility trajectories, retrieval events, production creation/compilation events, and other ACT-R diagnostics that were pre-specified before data collection.

---

## 7. ACT-R capability envelope

H2 must challenge the **full legitimate ACT-R realization stipulated by this experiment**, not the intentionally constrained H1 model.

The admissible capability envelope includes, where required by the formal learner design and supported by the chosen ACT-R release:

- procedural production matching and conflict resolution;
- utility learning;
- declarative memory and retrieval;
- chunk creation;
- goal/imaginal state where used by the model;
- partial matching where required and explicitly parameterized;
- spreading activation where required and explicitly parameterized;
- production compilation when it is part of the stipulated learning account;
- other standard ACT-R mechanisms only when explicitly declared in the model specification.

The envelope does **not** permit arbitrary additions after observing H2 results.

For every enabled mechanism, the pre-registration must specify:

- why it belongs to the legitimate ACT-R account under test;
- exact parameter values;
- initialization state;
- learning switches;
- whether stochasticity is enabled;
- what observable consequences are expected.

For every disabled mechanism, the specification must state why exclusion is legitimate for this particular task.

A residual claim is inadmissible if the discrepancy can reasonably be removed by enabling a standard ACT-R mechanism that belonged to the pre-declared capability envelope but was omitted from the tested implementation.

## 8. ACT-R forward-model requirement

No H2 empirical execution may begin until the exact ACT-R model has generated **prospective forward predictions** from the frozen training fixtures.

The forward model must produce, before future-task data are observed:

`training fixture → ACT-R internal state at block boundary → predicted distribution for A/B/C/D trajectories`

Predictions must be generated independently for every stochastic seed included in the pre-registration.

At minimum the prediction package must specify:

- expected first-trial action distribution;
- predicted mean and distribution of trials-to-criterion;
- predicted cumulative error trajectory;
- predicted transfer performance;
- predicted interference cost in D;
- predicted production/utility or retrieval signatures used to explain the trajectory.

No parameter may be tuned using future-condition outcomes.

The forward-prediction package becomes immutable once the first H2 empirical condition is executed.

---

## 9. Stochasticity and distributional prediction

H2 does not treat one trajectory as a deterministic signature unless the model itself is deterministic.

For every stochastic ACT-R realization:

- a fixed primary seed set is declared before execution;
- an independent replication seed set is declared before execution;
- the observed trajectory is evaluated against the pre-generated distribution;
- single-seed agreement is not sufficient to establish adequacy or failure.

The primary model-comparison unit is therefore a **distribution of trajectories**, not a single trajectory.

---

## 10. ACT-R failure adjudication hierarchy

An apparent discrepancy must be adjudicated in this exact order:

### Level 1 — Data / implementation integrity

Check fixture hashes, trial counts, interface events, feedback timing, logging integrity, and runtime completion.

### Level 2 — Representation integrity

Determine whether the tested ACT-R representation actually had access to the information stipulated by the learner interface. A representation defect is not an architectural residual.

### Level 3 — Parameter integrity

Test only the pre-registered parameter space and explicitly declared sensitivity region. Post hoc parameter search is prohibited from becoming an explanatory rescue.

### Level 4 — Stochastic adequacy

Determine whether the observed trajectory lies within the model's precomputed stochastic range.

### Level 5 — Legitimate ACT-R mechanism audit

Determine whether an established and pre-declared ACT-R mechanism that was omitted from the active realization can explain the discrepancy. If yes, the discrepancy is an incomplete implementation, not a residual.

### Level 6 — Replication / trajectory stability

Repeat under independent seeds and/or an independently frozen future trajectory. A one-off anomaly is insufficient.

### Level 7 — Architectural adequacy test

Only after Levels 1–6 survive may the discrepancy be classified as evidence against the tested ACT-R account.

Even then, the result is a **candidate architectural residual**, not an understanding construct.

---

## 11. Residual criterion

A candidate residual requires all of the following:

1. a formally defined observable phenomenon;
2. a pre-specified ACT-R prediction;
3. a verified implementation;
4. a reproducible discrepancy across the relevant future-learning conditions;
5. failure not attributable to fixture, interface, representation, parameter, stochasticity, implementation defect, or omitted legitimate ACT-R mechanism;
6. persistence under an independent trajectory or seed set;
7. evidence that the discrepancy is about the **learning consequence of prior experience**, not merely immediate task difficulty.

A rival model outperforming ACT-R is neither necessary nor sufficient for the residual claim.

---

## 12. What H2 is not allowed to conclude

H2 may not conclude, solely from its result, that:

- the learner understands the relation;
- an internal understanding state has been observed;
- relational abstraction equals understanding;
- consciousness has been demonstrated;
- a new psychological construct is required;
- an architectural residual exists merely because ACT-R is less predictive than a rival model.

Any such conclusion requires a separate evidential argument.

## 13. Pre-execution locks

The following six items must be complete before H2 is executable:

### Lock 1 — Formal world

Exact training and future trial fixtures, contingency tables, feedback rules, and cryptographic hashes.

### Lock 2 — Learner interface

Exact observable information stream, permitted feedback, timing, and exclusions.

### Lock 3 — ACT-R capability envelope

Exact model architecture, enabled/disabled mechanisms, parameters, initialization, and stochastic seed policy.

### Lock 4 — Training regime

Exact training order, matched-history construction, immediate-performance matching criteria, and rejection rules.

### Lock 5 — A–D transformations

Exact mathematical definition of each changed variable and each invariant variable, with controlled complexity and exposure counts.

### Lock 6 — Prospective predictions

Frozen quantitative ACT-R predictions and uncertainty ranges for every primary measure in A–D, generated before empirical future-task execution.

**H2 remains NON-EXECUTABLE until all six locks are signed off.**

## Governing principle

> **Do not call a structure latent because the experimenter can see it. Define exactly what the learner sees, exactly what regularity exists in those observations, and exactly what the surviving architecture predicts will happen next.**

And the residual boundary remains:

> **A model-discriminating phenomenon is not an architectural residual merely because the models disagree; the residual begins only when the surviving account cannot adequately explain the observed future-learning phenomenon after legitimate mechanisms and alternative explanations have been adjudicated.**
